# Capturing and measuring the running game

How to photograph what the running game draws, measure it, and read its state without pixels.

## Capturing
- **A cover that spans a LEVEL LOAD is photographed by one uninterrupted capture loop started at the press**, never the settle-then-shoot cadence: the whole thing is over in about four seconds and a settle lands after it. Timestamp each frame and read the sequence back - that is what says whether anything else was on screen in between.
- **Judge a settled capture numerically** — PowerShell `System.Drawing` `GetPixel` against measured colour targets, never by eye. (The settle protocol itself is in the instructions.)
- **A single captured frame missing EVERY widget - an always-on overlay included - is a capture artifact, not a flash.** GDI grabs race an uncapped present, and the quality window runs the game uncapped for its whole measurement. Nothing the game does can drop one overlay and the always-on one together, so the always-on overlay's absence is the tell.
  - With no always-on overlay to look for, ask: **is the frame's UI a state the widget tree can be in at all?** One showing the chrome hidden but not the overlay that hides it is torn, not real. Settle it against a per-frame log from inside the game, never against neighbouring captures.
- **To answer "how many frames render like this" — or prove "no frame ever shows X" — instrument rather than photograph**, since captures miss single frames: one `UE_LOG` per frame naming `GFrameCounter` and the state, from the widget's own tick or from `FSlateApplication::OnPostTick` in a throwaway .cpp, driven through `-game` (`drive-game.ps1`), count the offending lines, then revert. It names the first and last frame by number, which a capture at 60Hz cannot, and it is the only thing that can adjudicate a suspect frame.
- **The settle protocol does NOT apply to a TRANSIENT that expires** (a readout holding ~3s): what it defends against is auto-exposure wash on *entering* a scene, already satisfied by any drive that has been in the match for minutes. Confirm the pre-trigger state with a passive `Snapshot`, then capture immediately and repeatedly from the instant you send the one triggering input. To make the trigger's timing predictable at all, prefer a fixture state where the game **waits for the player indefinitely**.
- **To photograph a ~200ms animation, capture a SMALL REGION and fire the input from inside the capture loop.** A whole-window `CopyFromScreen` is too slow to sample it; a 65x30 crop around the moving element samples every ~15-25ms, and scanning one pixel row for the moving run's x-range per frame gives a position-vs-time table instead of an eyeball judgement.
- **A live drive cannot observe a decision window it keeps answering.** The moment the state is confirmed, STOP sending input, then wait and capture: `Snapshot`/`Screenshot` are passive, every `Type` is an input.
- **To prove an oscillating effect is running (or not), sample one pixel across several passive captures** rather than judging brightness by eye — six `Screenshot`s ~0.9s apart with NO input between, then `GetPixel` at the same coordinate: a pulse walks, a steady glyph reads the same every frame.
- **Falsifiable visibility diagnosis:** to prove a surface is actually rendered from a camera, substitute an extreme debug colour on its material and whole-frame pixel-diff settled before/after above TAA noise. Zero diff = not visible.

## Reading state without pixels

- **`Snapshot`'s text tree has no label for every UMG widget class.** `UProgressBar` reliably appears; `URadialSlider` (the `AdvancedWidgets` module) is silently omitted, not shown as `generic` or an error, and no `UBorder` node has ever appeared. Container/decoration widgets are broadly unlabeled. Don't treat a missing node as proof a widget failed to construct — cross-check `GetLogEntries` for construction errors AND an independent headless run reading the widget's own state; only trust "it's not there" if both are clean. When precise widget-class verification matters and Snapshot won't show it, state the limitation rather than claim proof.
- **A menu's highlighted row is invisible in the Slate tree** — no marker of any kind. Which row is highlighted can only be read from a capture.
- **Re-`Observe` a subtree ref before re-`Snapshot`ing it** — reusing a stale `ref:""` loses the game-widget tree entirely.
- The text tree proves widgets exist and transition, but CANNOT say which texture or colour a node is bound to. For an icon-set swap, fall back to the responsible dev-exec command's own `UE_LOG` line as proof the STATE changed, and say plainly that the visual result is unverified.
